# memex

Scaffolded by devstack. Dev URL: https://app.memex (prod: https://app.memex).

Inside the container this folder is `/srv/proj` (VSCode: Remote-SSH →
`memex` → open `/srv/proj`).

Web app: TypeScript, Hono + zod API, React + Mantine UI with TanStack Router,
built by Vite. **Agents and developers extending it: read [AGENTS.md](AGENTS.md).**

| Path | What |
|---|---|
| `server.ts`, `src/server/` | Hono API server, run by systemd unit `memex-app` (127.0.0.1:8080) |
| `src/shared/` | zod schemas shared by API and web app |
| `web/` | React app source (Vite root) |
| `static/` | build output of `pnpm build`, served by Caddy (gitignored) |
| `error/` | Caddy's error / catch-all page |
| `scripts/` | `sync-env.sh` (installs `infra/apt-packages.txt`, then `pnpm install --frozen-lockfile`, then the pinned yt-dlp), icon font, web font and CSP check scripts, the archive CLI |
| `scripts/runners/` | the runners `ytdlp` (downloads videos) and `encode` (ffmpeg: HLS and images), declared on the host |
| `vendor/` | the pinned yt-dlp release (`pnpm yt-dlp install`, gitignored; pin in `infra/yt-dlp.lock`) |
| `e2e/` | Playwright browser tests (Debian's Chromium), run with `pnpm test:e2e` |
| `infra/` | generated by devstack: unit copy, compress script, `devstack-requires.toml`; yours: `Caddyfile` (`caddy.manage_caddyfile = false`), `apt-packages.txt` |
| `infra/sbom/` | generated CycloneDX inventory of the container and the app (committed) |
| `AGENTS.md` | how the app is built and how to extend it, and what the container enforces (app and runner sandbox contract) |
| `ideas/` | design notes for features |

Common commands (inside the container):

```sh
./scripts/sync-env.sh                     # after cloning or pulling: apt + pnpm deps
pnpm build                                # build static/
pnpm test                                 # vitest: unit + API integration tests (memex_test database)
pnpm test:e2e                             # browser tests against https://app.memex
pnpm archive search "report"              # the archive from the command line (JSON out)
pnpm archive add video <url> --wait       # queue a video download and wait for the entry
pnpm yt-dlp update                        # pin and install the latest yt-dlp (when a site breaks)
pnpm dev                                  # rebuild static/ on change
sudo devstack-sync restart app            # after editing server.ts or src/
journalctl -u memex-app -f                # app logs (no sudo needed)
./infra/compress-static.sh error          # after editing the error page
sudo devstack-sync reload caddy           # after editing infra/Caddyfile
sudo devstack-sync status                 # services, egress profiles, last package sync
curl -s https://app.memex/api/health      # the app through Caddy (the container trusts the dev CA)
```

More in [AGENTS.md](AGENTS.md#commands).

Call the app through Caddy (`https://app.memex`), not on port 8080: without
Caddy's internal token the app answers every request with a bare 500. Node trusts the
dev CA through `NODE_EXTRA_CA_CERTS`, which login shells get from
`/etc/profile.d/devstack-ca.sh`; set it yourself for processes started another way.

## What runs where, and with which rights

- **You, VSCode, extensions, terminals and coding agents** all run as `dev`.
  It has no general root: `sudo` only runs `devstack-sync` (the commands above).
  Root for you is `incus exec memex -- bash` from the host. It has full internet
  access, but the host and your LAN are blocked by an incus network ACL on the host.
- **To add a system package**, add a line to `infra/apt-packages.txt` and run
  `scripts/sync-env.sh`. Never `apt-get install` by hand: it isn't allowed, and a
  hand-installed package is gone on the next rebuild. Services that a package ships
  are masked; a service the app depends on is a devstack change on the host.
- **The app** (`memex-app`) runs as `memex-app`. What it may reach going out is
  its egress profile (`app.profile`, here `local`: loopback only, no DNS), enforced by
  nftables. Its only writable folder is `$STATE_DIRECTORY` (`/var/lib/memex-app`, a
  persistent volume). You can read that folder but not write it: writes go through
  the app. The archive's files live in `archive/` there and its metadata in Postgres, so a
  consistent backup needs **both** `devstack data backup` and `devstack db backup` on the host.
- **Runners** (`[[app.runners]]` in the devstack config; none yet) are for tools that
  need the internet or parse untrusted files. Each connection to a runner's loopback
  port starts one job as a separate runner user: public internet, no loopback, no
  secrets, and it can only write `$INCOMING_DIR` (`/var/lib/memex-app/incoming`;
  a runner has no `StateDirectory=`, so `$STATE_DIRECTORY` is unset there). Treat
  everything in `incoming/` as untrusted input. Note that an app that may send a runner
  any URL can reach the internet through it. The whole runner contract is in
  [AGENTS.md](AGENTS.md#runners--the-full-contract).
- **Tests**: the integration test database is `TEST_DATABASE_URL` in
  `~/.config/devstack/memex.env` (with `DATABASE_URL` for dev tools; e.g.
  `node --env-file-if-exists=$HOME/.config/devstack/memex.env`). Make test setup
  refuse to run unless the database name ends in `_test`.
- **Git**: `.git/hooks` and `.git/config` are read-only in the container (the host
  runs what's in them), and `git` is not installed here: commit from the host.

`infra/devstack-requires.toml` is what this project needs from its container: image,
Node, Postgres, app and Caddy settings, and the host folders it expects mounted (by name
and container path only). It holds nothing about any host, so it stays in git. Your own
devstack config (host paths, ssh, DNS, and where each mount comes from) stays outside
the repo. To build the environment on another machine: clone this repo, run
`devstack init --project <this folder>` (it takes the requirements as defaults and asks
for each mount's host folder), read the config it wrote, run `devstack up -c <it>`,
then `devstack db restore <dump>`, then `./scripts/sync-env.sh && pnpm build` inside
the container.

GPU passthrough is enabled for this project, but `devstack-requires.toml` does not
record it: turn it on in your own devstack config when you rebuild elsewhere.

## Trust boundary

The container is where untrusted code (npm packages) runs, but two channels reach the
host by design: ssh / VSCode Remote-SSH into the container, and this project folder,
which is shared **read-write** with the host. Treat anything in this folder as untrusted
when you run it on the host (`.vscode/`, `package.json` scripts, shell scripts).
`.git/hooks` and `.git/config` are mounted read-only inside the container
(`project.readonly_paths`); add other paths the host runs from there.

Inside the container, the app and runners can't do more than their profiles allow,
even if their code is edited. The container user (and so every agent) can still use
the real database as the app role, read the app data and use the internet: that is a
deliberate trade-off for development, not something the isolation prevents.

## Dependencies

The **inventory** is generated, not written by hand: `infra/sbom/container.cdx.json`
(everything installed in the container: Debian packages, Node, Caddy, Postgres) and
`infra/sbom/app.cdx.json` (this project's npm packages, from `pnpm-lock.yaml`).
Both are [CycloneDX](https://cyclonedx.org/), produced by
[syft](https://github.com/anchore/syft) inside the container, and both are committed.

```sh
./devstack sbom show            # what is in them (on the host)
./devstack sbom generate        # refresh them after changing a dependency
./devstack sbom check           # fails if they no longer match the container
./devstack sbom scan            # grype: known vulnerabilities in what is committed
```

`devstack up` refreshes them for you. They are normalized so the bytes depend only on
the dependency set: no timestamps, no run-to-run ids, so a diff means a real change.
Do not hand-edit them — `sbom check` is the gate, and a manual edit just fails it.

What this section is for is the part a generated inventory cannot hold — **why**:

- Runtime npm dependencies (`dependencies`) are only what `server.ts` loads in
  Node. Everything bundled into the browser by Vite is a `devDependency`: it is
  needed to build `static/`, not to run the server. Adding a runtime package is a
  decision; note it and the reason below.
- npm packages come in through pnpm with a committed `pnpm-lock.yaml`. Never
  `npm install` into this project.
- System packages go in `infra/apt-packages.txt` (Debian names only) and are installed
  by `scripts/sync-env.sh`. Never `apt-get install` by hand: it is not allowed, and a
  hand-installed package is gone on the next rebuild.
- Third-party apt repos and downloads are only used with a pinned signing key or a
  pinned sha256, checked before use, so a swapped download fails the build instead of
  being trusted. Those pins live in devstack, not here, except for yt-dlp (below).
- An entry in `sbom.ignore` (a vulnerability the scan should stop counting) is a
  decision too: record the id and why, here.

Runtime npm dependencies:

- **hono**: HTTP framework for the API: routing, middleware, typed responses, and
  `hono/client` (`hc`), which gives the web app a client typed from the server's
  routes. Small, standards-based (`Request`/`Response`).
- **@hono/node-server**: adapter that runs a Hono app on Node's `node:http`.
- **zod**: schemas shared by server and client (`src/shared/api.ts`): request
  validation on the server, response parsing and inferred types on the client.
- **hono-openapi**: the `validator()` middleware (wrapped by `src/server/validate.ts` for a
  compact 400 body; typed `c.req.valid()`) records each route's inputs, and `describeRoute` /
  `openAPIRouteHandler` turn routes plus the zod response schemas into `/api/openapi.json`,
  so the spec for agents cannot drift from the code. Replaces `@hono/zod-validator`.
- **drizzle-orm**: type-safe query builder and schema in TypeScript
  (`src/server/db/schema.ts`); the archive's queries are plain builder calls. Chosen so that
  frequent schema changes are routine: the schema is the source of truth and its migrations
  are generated SQL that is reviewed and committed.
- **postgres** (postgres.js): the Postgres driver under drizzle. Plain TCP, which the service's
  sandbox needs (`AF_INET` only, no unix socket).
- **pino**: structured JSON logging to stdout, which journald stores
  (`journalctl -u memex-app -o cat | jq`). Fast and the de-facto standard on Node.

Build and test tools (`devDependencies`):

- **drizzle-kit**: generates the SQL migrations in `drizzle/` from `schema.ts` (`pnpm db:generate`).
  It never touches a database; migrations are applied by `src/server/db/migrate.ts`. Its
  `esbuild` build scripts are denied in `pnpm-workspace.yaml` (`allowBuilds`): they only verify a
  binary that the platform package already ships.
- **vitest**: unit and API integration tests (`pnpm test`). Same Vite pipeline as the app, runs the
  `.ts` sources as they are.
- **hls.js** (pinned 1.7.3): plays an archived video's HLS stream in the browser through Media
  Source Extensions (`web/src/modules/archive/types/video/View.tsx`, loaded only on that page).
  No dependencies, no install scripts; its worker comes from a `blob:` URL, which the CSP's
  `worker-src` already allows.

- **react, react-dom**: UI library. `react-dom/server` is also used at build time
  (`vite.config.ts`) and by `pnpm check:csp`.
- **@mantine/core, @mantine/hooks**: component library / UI system. Runtime `<style>`
  injection is turned off for the CSP; see AGENTS.md "CSP rules".
- **@tanstack/react-router**: client-side router with type-checked paths, params and
  loaders.
- **vite**: bundler and dev server: builds `web/` into `static/`. Also hosts the
  `mantine-static-css` plugin (`vite.config.ts`) and the SSR used by `pnpm check:csp`.
- **@vitejs/plugin-react**: JSX/TSX transform and React Fast Refresh for Vite.
- **postcss, postcss-preset-mantine, postcss-simple-vars**: Mantine's recommended
  PostCSS setup for `*.module.css`: `rem()`, `light-dark()`, breakpoint
  mixins/variables.
- **typescript**: type checking only. Node runs the server's `.ts` directly by type
  stripping, so the server has no build step (hence `erasableSyntaxOnly`).
- **@types/node, @types/react, @types/react-dom**: types.
- **@playwright/test**: browser automation and test runner. Drives Debian's
  `chromium` through `executablePath` in `playwright.config.ts`. Tests in `e2e/` load
  the app through Caddy, so they run under the real CSP.

System packages (`infra/apt-packages.txt`):

- **woff2**: Google's WOFF2 encoder: converts the TeX Gyre OTF sources to `.woff2`
  for the web. Only needed when regenerating fonts; the output is committed.
- **chromium**: headless browser for Playwright at `/usr/bin/chromium`. Taken from
  Debian rather than `playwright install` so it comes from a signed repo and gets
  security updates through apt.
- **git**: reading the history from inside the container (writes happen on the host).
- **ffmpeg**: the `encode` runner (HLS remux, poster, thumbnail, animated AVIF preview with
  SVT-AV1); yt-dlp also uses it to merge video and audio. Runs only inside the runners' sandbox.
- **unzip**: unpacks the pinned yt-dlp build into `vendor/` (keeps the binary's executable bit).
- **gpg**: `pnpm yt-dlp update` checks the release's signature with it.

yt-dlp (neither apt nor npm): the official release's **bundled Linux build** (`yt-dlp_linux.zip`,
x86_64: yt-dlp with its own Python, plus `curl_cffi`, which yt-dlp needs to impersonate a browser
for some sites such as YouTube's subtitles), pinned by version and sha256 in `infra/yt-dlp.lock`,
unpacked into gitignored `vendor/yt-dlp/<version>/` by `pnpm yt-dlp install` (`sync-env.sh` runs
it) after checking the pin, with `vendor/yt-dlp/current` pointing at it. The previous version
stays unpacked so a running job isn't pulled from under it. Chosen over the pure-Python zipapp
(no `curl_cffi`, so more refusals) on 2026-10-11. Debian's package is far behind, and sites
like YouTube break old versions within weeks, so updating has to be one command:
`pnpm yt-dlp update [version]` accepts a release only if its `SHA2-256SUMS` carries a good
signature from yt-dlp's signing key (`infra/yt-dlp/public.key`, fingerprint
`AC0C BBE6 848D 6A87 3464 AF4E 57CF 6593 3B5A 7581`), then writes the new pin. Review the lock
change like a lockfile change. No 7-day wait as for npm: a fix for a site change is urgent.
It only ever runs inside the `ytdlp` runner's sandbox.

Deliberately not used, so they are not added without a reason:

- **A second DB library, a query-result cache, or raw SQL strings in routes**: drizzle's
  builder covers the archive; raw `sql` is only for what it cannot model (full-text search).
- **zustand, TanStack Query**: URL search params and route loaders are enough for client state.
- **A logging wrapper (loglayer)**: pino is used directly through a small `Logger` interface.
- **MCP / WebMCP**: the HTTP API with its OpenAPI spec, plus an accessible UI, is the agent interface.
- **React component tests (jsdom, Testing Library)**: the Playwright tests cover the UI.
- **Mantine `AppShell`, `Grid`, `SimpleGrid`, responsive style props**: they inject
  runtime `<style>` tags that the CSP blocks. Use CSS modules instead.
- **`'unsafe-inline'` in `style-src`**: Mantine's CSS variables are rendered to a
  static file at build time instead (`vite.config.ts`).
- **A data-fetching library (TanStack Query, SWR)**: route loaders cover the
  current needs.
- **Debian's `nodejs` package / NodeSource**: an exact, signature-verified Node release
  is pinned instead.
- **Docker**: an incus system container gives a full systemd userland that mirrors
  production (Caddy, the app unit and Postgres as services).
- **A build step for the server**: Node runs the `.ts` sources directly. Only the
  browser app is built (Vite).
- **`playwright install` / Playwright's browser builds**: downloaded from
  Playwright's CDN without a signature check (carried over from v1, unverified), and
  not updated by apt. Debian's `chromium` is used instead. If a Playwright upgrade
  stops working with Debian's Chromium version, pin `@playwright/test` rather than
  switching.
